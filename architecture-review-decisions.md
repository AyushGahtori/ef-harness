# Decisions from the external architecture review

This record describes proposed changes to the design. The operational tests below are acceptance scenarios for implementation. Document validation and diagram rendering do not demonstrate that the future harness passes them.

| Review area | Design adopted | Observable check |
|---|---|---|
| A · conflicting roles and flows | Code owns mutations. Planners own requirements, skill selection and integration. A worker asks its owner. A focused question queue reaches the developer. Execution control is the working fourth route. | Follow the same submitted change in the overview and detailed diagrams. The same owner decides and the same coordinator publishes. |
| B · false coverage, omissions, deferrals | Ground each claim in a typed source, check semantic support and derivation premises, distinguish current-scope blockers from explicit future milestones, and inspect applicable cross-cutting concerns. Count each criterion once. | “Use the link on a phone” supports mobile access. The offline and native choices remain open. A superseded premise reopens only its dependent claims. A deferred provider choice can release independent tasks, while its consuming task stays held. |
| C · routing races | Sequence submitted messages. Tie answers to focused question/version at input, reconcile mixed intents, and validate targets at delivery. Emergency stop goes directly to code. | Two planners ask questions and the user says “yes.” It applies only to the bound question. A later steer that retires that question cannot be answered by accident. |
| D · uncertain holds | Scope holds by the affected contract, record separate reasons, reconcile in-flight operations and preserve or reconstruct worker context. | User pauses email and requests print. Resolving print cannot remove the explicit pause. A completed external send remains recorded even if the task is superseded. |
| E · stale work and publication | Validate versions of read or changed nodes and semantic invariants, publish a coherent snapshot, serve active briefs centrally, and deliver durable updates after activation. | Concurrent disjoint edits both publish. Competing cutoff edits produce a conflict or an explicit supersession. Interrupt staging and notification separately. Readers observe a complete revision in either case. |
| F · self-verification, isolation and split-brain | Planner defines expectations first. Independent verification uses fresh scoped resources, pinned contracts and a current lease. Author integrates at the actual feature entry point. | Reject a changed protected expectation, an empty test run, a stale lease and conflicting fixtures. Exercise two concurrent apps, isolated state and a production-path journey. |
| G · handoffs | Tie claims to verified artifacts and versions. Bound wait chains and resolve cycles through the owner. Treat returned text as project data and restrict outbound context to permitted inputs. | A handoff containing instructions cannot grant new tools or change authority. A consumer gets the exact accepted artifact, or a missing-input response. |
| H · cost and operations | Reserve budget atomically, bound repairs, check structured outputs, isolate tools and recover pending externally visible effects. | Concurrent workers cannot each claim the last budget reservation. Repeated identical failure stops the affected scope. A paid timeout never causes a blind second charge. |
| I · missing workflows | Pinned brownfield observations, applicability review, scoped human prerequisites, explicit delegated choices and a single-desktop ownership model. | Existing behavior that differs from the desired behavior is recorded with its source. A missing OAuth setup blocks its consumers and leaves independent work available. |
| J · evaluation | Freeze input artifacts and hidden expected decisions. Measure false resolutions and repeated questions as well as time, cost and useful decisions. | Replay scripted answers first. Evaluate a separate recorded/persona run on a new project, a CLI, and a backend. Report false answers by decision type and model tier. Keep answer keys unavailable to the interviewer. |

## Which suggestions changed

- Retain automatic progression and an immediately available stop. No fixed countdown or universal confirmation screen. Instead, order the ready queue so tasks whose transitive decision closure contains only `explicit` user facts dispatch ahead of tasks that depend on `derived` or `delegated` choices, giving a zero-delay buffer while the developer sees the change summary. Use explicit scope boundaries and existing authority for irreversible, costly or externally visible actions. A technology choice can be delegated within the user's constraints.
- Preserve independent work packages and author-led integration. Consecutive assignment is a useful default for comparable tasks. A scheduler may redistribute unstarted independent work when estimates or resource needs differ, preferring `explicit`-grounded tasks first.
- Retain greedy marginal coverage. Stable criterion IDs are the durable representation. Temporary sets or multiword masks can be benchmarked against each other. A profile must justify more complex indexing.
- Use a two-tier verification policy rather than blanket mutation score thresholds. Make planner-owned expected values, input-only binding, **red-before-green** against the pre-change base/stub, and **at least one held-back example on rule-bearing logic tasks** the default baseline, closing no-op bindings and literal example hard-coding at negligible CPU cost. Add property generators, targeted boundary mutation probes or repeated clean runs selectively where task semantics warrant them, and calibrate thresholds from project data.
- Keep catalog effort ratings, inference thresholds, recovery timing, strong-model escalation points and resource caps configurable and evaluate them before choosing production defaults. Use test data that reflects the real backing service when emulator behavior differs.
- Keep the public repo untouched. The frozen baseline uses the existing commit and blob hashes. The prior 5,775-line result describes the local working tree including extra files. [Manifest](resume-changer-benchmark.json)

## Build order and failure injection

1. Before parallel dispatch, implement coordinator validation, scoped budgets, leased workspaces, current briefs and independently executed checks. Verify a returning replaced worker, concurrent use of one resource name, duplicate assignment, a zero-test pass and a changed acceptance file.
2. Before automatic start, verify quote support, scoped deferrals, prerequisite inheritance and a focused question queue. Try a retracted spoken idea, a misheard time, a stale reply, a qualified delegation and a complete request requiring zero visible questions.
3. Before multi-feature publication, verify per-node read/write validation, semantic conflicts, rollback as a new revision and durable notification delivery. Interrupt before activation, after activation and during an external effect. Also test unrelated changes and a burst of steers on the same feature.
4. Before claiming efficiency, compare these results on pinned inputs with a short-prompt baseline. Count supported decisions carried to an executable test, false confirmations, unnecessary holds, duplicate side effects, costs and elapsed time. A simulation is repeatable when its facts, answer mapping, versions and settings are frozen. A stochastic persona alone is insufficient.
