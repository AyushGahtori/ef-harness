# Coding harness architecture

A developer can describe a project for an hour and still leave an important choice unstated. The harness turns the conversation into decisions with evidence, asks about gaps that change the build, and gives each worker just the information it needs. The developer sees one chat and a readable architecture. Behind it, the harness tracks which rule, task, test and agent each change affects.

Start with the [README](README.md) for orientation and the [roadmap](roadmap.md) for build order. The end-to-end assembly line is in [build pipeline](build-pipeline.md).

**Design, not an implementation report.** This is the proposed contract for the first desktop version. It keeps automatic progression through discovery and planning, independent task batches and planner-led integration; the first build of a project waits for the developer's **Start build** on the plan preview. The review changed who may commit a decision, what counts as complete, and what qualifies as a verified feature. ## 1. One conversation, two ways to start

Minute zero has two steps. **Connect AI:** pay per token with API keys, use a plan the developer already pays for (Sign in with ChatGPT; or the developer's own Copilot, Cursor or Gemini CLI login, which our harness supervises without an AI of its own; Claude is used with an API key only), or run a local model. Plan work is budgeted in *allowance*, API work in dollars, under one reservation rule. **Pick a folder:** Git is required and bundled; an empty folder gets a repo, a dirty one gets a read-only snapshot, and the developer's checkout is never touched. The app is a window over a per-user background daemon, so closing the window never kills a build; every agent command runs in an OS-enforced sandbox with no direct internet. [Provider connections](provider-connections.md) · [Agent runtime adapters](agent-runtime-adapters.md) · [Workspace and Git](workspace-and-git.md) · [Desktop app](desktop-app.md) · [Sandbox and security](sandbox-and-security.md) · [Worker loop](worker-loop.md) · [App shell and governor](app-shell-and-governor.md) · [Kernel schema and protocol](kernel-schema-and-protocol.md) · [External intake](external-intake.md)

The developer can type or dictate. **Talk it through** shows all five prompts with examples folded. **One question at a time** opens the current example. Either mode accepts one long story, skipped questions and answers arriving out of order. Dictation becomes local text only; a pause, even a long one, never submits. The architecture canvas updates once, after Send, with changes highlighted. Only submitted input can change scope, plans or worker assignments. The canvas beside the chat is clickable: select a box and talk about it. [Interactive architecture](interactive-architecture.md)

The five prompts ask: **What are you building? Who needs it and why? What happens in one successful use? What must the first demo prove? What is fixed and what may we choose?** For the workflow question, “staff submit lunch choices and the kitchen sees totals by dish” is enough: actor, action, observable result. We can learn who may edit after cutoff later. “Choose a free local database for this demo” delegates a bounded choice. “I don’t know” asks for help; an empty answer supplies no evidence. [Opening rubrics, versioned prompts and examples](opening-prompts.md) · [First-run experience](project-discovery.md)

For an existing codebase, index relevant docs, entry points and tests at a pinned commit. Keep what the repo *does today* separate from what the developer *wants next*. Preserve source path, revision and span so another worker can check a claim without rereading the entire project. The five prompts become five change prompts prefilled from a free local scan, and test health is measured once in an isolated copy. [Brownfield discovery](brownfield-discovery.md)

## 2. Select the next questions and establish readiness

The opening reviewer proposes the project domains. Code unions shared and matching domain indexes, then filters the versioned catalog by applicability, prerequisites, previous answers and deferrals. For each batch, pick the question with the greatest additional coverage, remove that coverage from a temporary scoring set, then score again. With 200 eligible questions and five slots that is at most 1,000 candidate scores; the resolver sees only the chosen entries, their rules and the relevant evidence. Use ordinary sets first; benchmark multiword bit masks before optimizing. Two or three questions may suffice for a feature change. If a needed decision has no entry, specialize or combine nearby general questions, or draft a new project-local question and rubric. Promotion to the shared library is a separate editorial decision.

Three small, versioned prompts do distinct jobs: **opening review** finds enough to start asking useful questions; **batch resolution** proposes one answer per criterion; **clarification** explains or asks about one remaining gap in the user's words. A cheap model is a candidate for these roles, not presumed accurate. Check author, exact source span, revision, allowed derivation and premises. Check that the quote supports the *meaning* of the proposed value. A quote about opening a link on a phone establishes neither offline support nor native apps. Superseding a premise reopens the facts that depend on it. Recommendations, retracted speech and a model’s earlier paraphrase cannot become user facts.

Show **what is known** separately from **what can start**. For example eight settled decisions out of twenty applicable ones is 40%. “Email the totals” settles channel, not recipient. Credit the known part now and clarify the other in the same batch, after submission. An explicitly deferred decision stays visible without receiving value credit. For a milestone, account for inherited project blockers and unresolved cross-cutting concerns. Defer behind a real interface only when independent work can proceed without guessing. Scope additions get a new baseline with an explanation. An empty scope or a percentage rounded to 100 cannot pass a readiness check.

Every batch offers **Accept all recommended**, and **Autopilot** keeps accepting recommendations until the architecture is complete, stopping only for must-ask decisions (purpose, money, personal data, identity, irreversible or legal choices). The project stage (Prototype, MVP, Production) changes the recommendations, so a prototype settles scale and compliance in one click. [Discovery depth and catalog](discovery-depth-and-catalog.md)

A short interview doesn't contain every screen state, permission and failure mode, so **spec expansion** generates them as matrices from the settled decisions, fills each cell with a recorded basis, and checks the whole set for contradictions by code before a model. Information is complete when every required cell is filled, no contradiction is open and no critical question remains. [Spec expansion](spec-expansion.md)

When all decisions **needed for the scoped architecture** are settled, including valid boundaries around deferrals, start constructing it automatically. If connecting the nodes exposes a gap, reopen it. The first build of a project waits on a **plan preview**: Phase 0 foundation, task graph, proposed crew, cost and time, with **Start build**. Later small revisions can auto-start under a threshold the developer sets. [Planning and crew](planning-and-crew.md) Coding starts only for a published task whose own prerequisites, contracts, authorization and operating budget are ready. Order the ready queue so tasks built solely on `explicit` user facts dispatch ahead of tasks that rely on `derived` or `delegated` choices, giving a zero-delay buffer while the change summary is visible. A detailed submission can pass several internal batches with zero questions shown. Keep Stop and the list of inferred or delegated decisions visible. ## 3. Two linked graphs, one writer

The **architecture graph** holds requirements, features, rules, interfaces, tasks, tests and document sections. The **runtime graph** holds project and feature planner roles, worker assignments, sessions, checkpoints and results. Typed edges distinguish “depends on” from “owns” or “verifies.” One cutoff rule can point to several consuming tasks and one responsible planner without duplicating the rule in every prompt.

For the first desktop version, a TypeScript coordinator is the sole SQLite writer for canonical graph and runtime state. Models propose typed actions; code checks identity, authority, operation ID, lease and relevant versions before applying them. The project has human-readable Markdown and Mermaid views plus a machine-readable JSON export at a named revision. They can be regenerated; editing a copy cannot secretly change a live worker’s brief. The router and workers request small, indexed graph slices from the coordinator. ## 4. Steer without disrupting unrelated work

Keep the bottom chat enabled during discovery, planning and execution. Give submitted messages a sequence and bind replies to the question and version focused when the user started answering. Multiple planners can ask, but one focused card owns an unqualified “yes.” Retiring a question retires that binding. A mixed message can contain several ordered intents: “Pause email, and tell me whether anything was sent.” The second clause reads recorded outcomes; it never triggers a send. An explicit Stop control reaches the coordinator directly.

The four working routes are a read-only question, a current-feature change (including a bug or requested revert), a new feature, and execution control. “Maybe add uploads” in submitted, unretracted speech enters this release unless explicitly deferred. Reuse an existing feature ID for a duplicate request. Resolve a target by explicit link, selected item, names, aliases and recent topics, then expand a small neighborhood if needed. The small router proposes a destination; code follows typed ownership to its current role holder. Ask which list the user means if the evidence does not distinguish the kitchen list from customer history.

For “the kitchen wants a printed list,” compare **add print** with **replace email**. Continue work shared by both readings. Hold a task affected under every reading at a safe tool boundary; a possibly affected task may finish its bounded step, but its result cannot be accepted until the contract is settled. Avoid irreversible effects while their authority or input is in doubt. Record hold reasons separately: clarifying print never cancels a user pause. Checkpoint the current brief, worktree and effects; preserve the session where usable and rebuild its context from the new brief if a rule contradicts it. Show a short change summary with an acceptance example; no blanket approval or countdown. ## 5. Plan, isolate and hand off work

Between information and code sits an assembly line: risk-triggered research with verified citations, system architecture, a master plan, then per-feature architecture and task files produced one wave ahead. Everything lives in one knowledge database; Markdown and Mermaid files are views. Graph compile refuses any plan where a requirement lacks a task and a check, and paperwork is capped at a share of the budget. Each worker gets a compiled packet of exactly the rules, contracts and edge cases its task touches, including cross-cutting rules matched by scope, and can pull more through logged read-only tools. [Build pipeline](build-pipeline.md) · [Knowledge slicing](knowledge-slicing.md) · [Prompt contracts](prompt-contracts.md) · [v1 knowledge corpus](v1-knowledge-corpus.md) · [Test environments](test-environments.md)

The project planner writes the master plan. Each feature planner writes a feature file, task files, and child tasks where justified. Leaf briefs contain behavior, paths, versioned interfaces, allowed tools, relevant skills, edge cases and independently checkable examples. UI briefs include visual and interaction states, and reference crops when supplied. The worker should be able to complete its task with the rest of the plan hidden. The planner selects required/optional versioned skills from the proposed catalog of about twenty; the coordinator provides the selected content. A task can require none.

Phase 0 builds the shared foundation first (scaffold, packages, base schema, shared types, auth skeleton, test harness, design tokens) from precise recipes a Junior model can follow. The crew is then computed per wave from the task graph's width, machine capacity, connection limits and budget, and each task gets a level (Junior, Mid, Senior, Manager) by difficulty and expected cost. For example, if a wave has twelve independent tasks and four workers fit, they can take 1–3, 4–6, 7–9 and 10–12 when effort is comparable. Reserve shared registries, migrations, lockfiles and contract wiring for their assigned owner. Where a fixture cannot replace a real dependency, make two batches. An available worker may claim **unstarted** independent work; an active task has one current lease. Give each attempt a workspace and separate ports, temporary files, browser profile and state namespace as needed. Prefer stateless fixtures, then disposable synthetic data; reserve engine copies or exclusive execution for tasks that truly require them.

Workers publish artifact references, contract versions and observed results. Peers can retrieve a specific artifact or send a focused request. A worker with a missing product decision asks its author; the author checks recorded evidence before queueing a user question. OpenCode child sessions or an OpenRouter-backed model call may perform work; neither is the source of shared state. Bound and detect circular waits. An agent summary cannot expand permissions or override the contract. ## 6. Verify the feature independently

Before implementation, the task author or separate specification writer records expectations from the requirements, including at least one held-back example for rule-bearing logic tasks. The coordinator confirms red-before-green against the pre-change base or a trivial stub, then protects the accepted examples, runner and relevant config. Worker checks are useful during development. Acceptance comes from a clean verifier executing the pinned expectations on the submitted artifact and recording what ran. Missing or skipped required cases cannot produce a pass. A bad expectation goes back to its owner with evidence; the implementer cannot change it to pass their own code. Screens are tested through a published interaction contract (route, button names, headings), API routes through their schema, migrations against a fixture at the previous schema, and AI features through a stub-model shell test plus a judged eval set. A failed hidden check climbs a hint ladder (rule and failure type, then a fresh disclosed example, then a stronger level or the author) instead of three blind guesses. [Verification for real apps](verification-for-real-apps.md) Before verification, a deterministic static audit rejects stubs, TODOs, swallowed errors, dead controls, hard-coded data and test tampering. [Completeness gate](completeness-gate.md) Mystery bugs run as investigations (reproduce, localize, prove, then fix) and repo-wide changes as sweeps with an exclusive lease and a compiler-driven checklist. [Investigations and sweeps](investigations-and-sweeps.md)

The planner who authored the task file still owns feature integration; a successor may take over the role with a new lease. The user’s 70% connecting / 30% reviewing describes the intended emphasis, not a required ratio. The integrator wires real entry points and runs the relevant journey, using Playwright for a browser feature. For example, two separate soup orders must produce one printed row with quantity two. A project merge queue tests the combined candidate against the current target. Passing four isolated tasks is not equivalent to shipping a working feature. Attribute failures to requirement, implementation, interface, test or environment before retrying. [Verification, integrity and isolation](verification-and-isolation.md) · [Integration graph](parallel-feature-integration.svg)

## 7. Publish revisions and recover

For “move cutoff to 10:45,” traverse reverse links from the rule to its architecture section, feature plan, backend task, UI label and boundary cases. The planner proposes one change. The coordinator validates the read and write versions of affected nodes and relationships, plus semantic constraints; an unrelated change elsewhere need not force a retry. Commit canonical state, versioned briefs, event and outbox atomically. Publish labeled exports derived from that revision. If rendering a view fails, retain its revision/status and retry; never serve a mixed or stale view as current. Reject stale worker authority. Recheck outputs against the contracts actually consumed; unrelated project edits alone do not invalidate a result. Undo creates a forward revision and any required work to revert merged code. [Publication and recovery example](linked-architecture-revisions.md)

Reserve money, tokens and execution slots before dispatch. Bound calls, integration, repair and rebase loops by budget, time and signs of progress. Throttling calls for bounded backoff. An unknown outcome, such as a send timing out after transmission, requires reconciliation rather than blind retry. On restart, recover the outbox, pending effects and leases before resuming dependent work. Steps that need a person, such as provisioning an account, hold only their consumers. [Operating rules and recovery](coordinator-and-recovery.md)

Work is checkpointed at every turn boundary, so hitting a budget or plan limit parks tasks instead of failing them: the developer can add budget, switch to cheaper models, wait for a plan reset or export the unfinished branches to finish by hand. Undoing a merged feature first inventories what it added and who else uses it; shared pieces and data stay unless explicitly removed. Reopening a project days later shows a reconciled welcome-back summary and runs nothing until **Resume**. The developer's own edits in VS Code are never overwritten; “I fixed it myself” runs the same clean verification and credits them. [Stops, undo and re-entry](stops-undo-and-reentry.md) · [Editor coexistence](editor-coexistence.md)

After landing, the harness can push its branches, open pull requests, repair CI failures in a bounded loop and deploy through host adapters, with every external change recorded as an approved effect and production migrations run expand-then-contract. Project knowledge travels with the repo on an orphan `harness-state` branch, one device or teammate writes at a time, and several projects share plans and laptop capacity through one broker. [Ship and deploy](ship-and-deploy.md) · [Projects, portability and sync](projects-portability-and-sync.md)

## 8. What the developer watches during a build

The **Board** shows lanes (working, waiting on you, held, verifying, done) with one-line statuses written by code from agent events, spend meters and one inbox. Questions are answered by their owners first, de-duplicated, grouped and batched; only critical items interrupt. Secrets go into the OS vault and are injected at run time, never into worktrees, prompts or Git. The optional **Office** view draws the same state as an animated company: workers at desks by level, managers in offices, the developer as CEO receiving papers when a decision is needed. UI work shares one Phase 0 design system and can be steered by pointing at elements in a live preview. ## 9. How we will know this helped

On the frozen Resume Changer commit, the manifest contains **73 Markdown docs; 17 whose filename stem contains “plan” or “task” total 4,906 lines**. The earlier 5,775 included local working files and is not the reproducible baseline. Line count describes the reference material, not its quality. Test whether discovery finds a real requirement (such as clearing selections on a library switch), whether an executable journey actually catches its violation, and whether fewer tokens and interruptions bought comparable or better results. Use fixed scripted turns, held-out expectations and more than one project type. Track false confirmations, missed blockers, duplicate questions, user corrections, resource cost and elapsed time. Prompts, skills, catalog packs and policies are promoted only through paired comparisons in the offline meta-lab, which also tests the harness itself by deterministic simulation with fault injection.
