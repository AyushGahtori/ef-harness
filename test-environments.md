# Test environments: starting, isolating and cleaning backing services

Four workers, two clean verifiers and the App preview may all need a Next.js dev server, Postgres, Redis, a mail catcher and a fake OAuth provider at the same time, on one Windows laptop that may not have Docker. The **environment orchestrator** is the daemon subsystem that provides these. The isolation rules it implements are in [verification and isolation](verification-and-isolation.md); the checks that use it are in [verification for real apps](verification-for-real-apps.md). Research: [test environments on Windows](research/test-environments-on-windows.md).

## Decisions in plain words

1. **Docker is optional.** Every v1 service has a native Windows path; Docker or WSL2 is used when available and needed for Linux parity.
2. **Share servers, isolate data.** One Postgres server per project hosts a separate database per environment; one mail catcher serves all environments with per-environment addresses. Servers are expensive in memory; databases are cheap.
3. **Every environment gets its own ports, URLs, database, temp folder and browser context,** injected through environment variables the app is required to read.
4. **Databases come from pre-seeded templates,** cloned per environment, so a fresh database is ready in about a second, not a minute.
5. **Every process the orchestrator starts belongs to a Job Object that dies with its owner,** so a crash leaves nothing behind.
6. **Test data is generated by code from the schema,** with edge cases taken from the spec. No tokens are spent on rows.

## What an environment is

An environment is created for an attempt, a clean verifier run, a migration check or the App preview. The project's environment manifest (written in Phase 0) lists the services the app needs and the variables that connect them.

```yaml
# environment manifest (Phase 0, P0.6)
services: [postgres, redis, mail, oauth]
app:
  start: pnpm dev
  ready: http GET /api/health == 200
env:
  PORT: "{port.app}"
  APP_URL: "http://{host}:{port.app}"
  NEXTAUTH_URL: "http://{host}:{port.app}"
  DATABASE_URL: "postgres://app:{secret.pg}@127.0.0.1:{port.pg}/{db.name}"
  REDIS_URL: "redis://127.0.0.1:{port.redis}/0"
  SMTP_URL: "smtp://127.0.0.1:{port.smtp}"
  OAUTH_ISSUER: "http://127.0.0.1:{port.oauth}/{env.id}"
```

## Services without Docker

| Service | Native Windows provider | Sharing model | If unavailable |
|---|---|---|---|
| SQLite | In-process; file copied from template | Per environment | — |
| Postgres | Embedded native Postgres binaries (Windows x64 builds exist), one server per project | Database per environment | Docker or WSL2 |
| Redis-compatible | A Redis-protocol server with a Windows build (e.g. Memurai's free developer edition or Microsoft's Garnet; chosen in the spike) | One server per project; each environment gets its own database index, or a small server of its own only when the app needs more databases than the index range allows | Docker or WSL2; or an in-process fake for unit-level checks only |
| Mail | Mailpit (single binary) | One per project; each environment uses its own recipient domain (`@env91.test`) and reads its messages through Mailpit's search API | — |
| OAuth / OIDC | A Node OAuth mock server inside the orchestrator | One server; issuer path per environment | — |
| Payments | stripe-mock for API shape; webhooks signed and delivered by the harness with the test secret | Per project | Docker |
| Object storage | A local S3-compatible server or a filesystem adapter | Bucket per environment | — |
| Other HTTP APIs | Record and replay (recorded once with approval, replayed offline) | Per environment | — |

Postgres versions follow the project's production target. If the project needs a Postgres extension not in the embedded build, the orchestrator requires Docker for that project and says why.

## Isolation

| Shared thing | How it is separated |
|---|---|
| Ports | Allocated from a reserved range (41000–48999), recorded in the database, released at teardown |
| URLs and callbacks | Built from the manifest with the environment's own ports; OAuth redirect URLs registered per environment in the mock |
| Cookies | Cookies ignore ports, so `localhost:41001` and `localhost:41002` share a browser cookie jar. Every Playwright run uses its own browser context, and every App preview uses its own Electron session partition. Where a test needs distinct hosts, the environment uses `env91.localhost` (Chromium resolves `*.localhost` to loopback). |
| Database | One database per environment, cloned from a template; dropped at teardown |
| Cache and queues | Separate Redis-compatible server or database index per environment |
| Files | Temp, upload and build output folders inside the attempt |
| Mail | Per-environment recipient domain |

**Hard-coded ports and URLs** (common in brownfield apps): brownfield discovery and the static audit flag literals like `localhost:3000`. Three options, offered in this order:

1. A small Phase 0 or brownfield task makes them configurable (recommended).
2. A Tier D container per environment, which gives each its own network namespace.
3. An exclusive “port 3000” resource lease, so environments needing it run one at a time.

## Templates and fast clones

```
migrations hash + seed recipe hash ─▶ template database tpl_<hash>  (built once, in the background)
                                          └─▶ CREATE DATABASE env_91 TEMPLATE tpl_<hash>   (per environment)
```

- A template is rebuilt only when migrations or the seed recipe change; building happens while workers are coding, before verifiers need it.
- Small templates clone in well under a second. Very fast copy-on-write cloning isn't available on Windows file systems, so templates are kept small: the **functional seed** (tens of rows per table, every edge case once) is the default. The **performance seed** (10,000+ rows) is a separate template cloned only for performance checks.
- A template database accepts no connections except during its build, which cloning requires.

## Synthetic data

Generated by code, deterministic per seed number:

1. **Order:** tables are filled in foreign-key order (topological sort of the schema); cycles are broken with nullable references filled in a second pass.
2. **Values:** typed generators per column (names, emails, prices, dates) from a seeded fake-data library and the locale decided in discovery.
3. **Edge cases from the spec:** every boundary named in spec items gets rows: names at maximum length, Unicode and emoji, right-to-left text, times just before and after a cutoff and around daylight-saving changes, zero, one and many children, soft-deleted rows, nullable fields left empty.
4. **Shapes:** realistic distributions (a few heavy users, many light ones) for performance data.
5. **Optional hints:** a planner may add per-entity hints (“dish names are lunch dishes”) once; the generator uses them as vocabularies. Rows themselves never come from a model.

Loading uses bulk copy, so 10,000 rows take seconds. **Migration checks** generate data at the *previous* schema version (the generator reads the schema at that commit), then run the new migration and its preservation checks ([verification for real apps](verification-for-real-apps.md#database-migrations-preserving-data)).

## Process supervision and cleanup

| Mechanism | Purpose |
|---|---|
| Project service Job Object (kill on close) | Postgres server, mail catcher, OAuth mock; dies if the daemon dies |
| Environment Job Object, nested | App server, per-environment services; killed at teardown |
| Process registry in `state.db` | PID, start time, port, environment; used for reconciliation. **Ports themselves are leased machine-wide in `global.db` (`port_leases`)**, so two projects never get the same port |
| Startup sweep | On daemon start, harness-owned processes not in a live environment are stopped; ownership is verified by PID and start time before killing anything |
| Readiness probes | Each service and the app have a ready check with a timeout; a failed start returns logs, not a hang |

## The App preview environment

A long-lived environment per project running from the persistent **integration worktree** ([workspace and Git](workspace-and-git.md#worktrees)) with a persistent “demo” database (functional seed plus anything the developer adds). The merge queue fast-forwards that worktree after each merge and then restarts the preview; demo data survives restarts. It is separate from all attempt environments.

## Starting servers from a task

Workers start long-running processes (dev server, a watcher) with the tool **`harness.start_service(name)`**, which asks the orchestrator to start that manifest entry inside the attempt's environment and returns its URL. The service lives until the attempt ends. A server started with `harness.run` dies when that command returns ([sandbox and security](sandbox-and-security.md#harnessrun)).

## Lifecycle API (inside the daemon)

| Call | Result |
|---|---|
| `env.create(kind, manifest, base_commit)` | Environment handle with allocated ports and database |
| `env.start_app()` / `env.start_service(name)` | Started and ready, or a startup failure with logs |
| `env.vars()` | The resolved environment variables |
| `env.reset_data()` | Re-clone the database from its template |
| `env.destroy()` | Kill processes, drop the database, release ports, delete temp folders |

Capacity limits (how many environments can run at once) come from the [hardware governor](app-shell-and-governor.md#hardware-governor).

## Edge cases

| Situation | Behavior |
|---|---|
| Embedded Postgres fails to start (antivirus, missing runtime library) | Clear error with the log; offer Docker; the task needing it is held, not failed. |
| A migration hangs on a lock | Statement timeout per migration in tests; reported as a migration defect. |
| Two environments need the same external sandbox account | Recorded responses where possible; otherwise an exclusive resource lease. |
| The app ignores `PORT` and binds 3000 anyway | Startup check sees the wrong port; the environment fails with “app ignores PORT”, which becomes a Phase 0 fix task. |
| Dev server leaks memory over hours | The governor restarts preview environments above a memory ceiling. |
