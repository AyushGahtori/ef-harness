# Adaptive discovery, coverage and steering

## Choosing a batch

The opening reviewer proposes domains from the five opening answers. A specific statement about a website with an AWS deployment activates the shared, web and AWS indexes. Opening review also considers existing-code constraints and cross-cutting criteria such as accessibility, privacy, reliability and scale when they affect the described workflow. For an existing repo, use a read-only inventory of visible contracts and tests with provenance. Repository observations describe current behavior. The user’s statement identifies desired behavior. Probe important uncertain scope such as in-app payments before activating an entire domain.

Store the catalog by stable question ID. Each entry declares domain tags, criterion IDs, prerequisites, a rubric, allowed inference rules and decision risk. The full entry schema, v1 domain packs, project stages and the must-ask list are in [discovery depth and catalog](discovery-depth-and-catalog.md). Start with sets of criterion IDs. They handle shared questions, retired criteria and new project-local IDs without changing bit positions. Bitsets are an optional optimization when profiling shows selection dominates. Any bitset implementation needs a revisioned stable ordinal map and support for more than one machine word.

1. Freeze the applicable decision and fact versions for this round. Combine the shared and active-domain lists, deduplicate IDs and filter by prerequisites. Exclude settled criteria, live questions already awaiting a reply, explicit milestone deferrals and later-release items.
2. Start a temporary set of uncovered eligible criteria. For each question count how many remaining criteria its rubric could settle. Prefer greatest new coverage, then the most blocking criteria, then a stable question ID. This tie-break can be evaluated on identical inputs.
3. Select the winner and remove its covered criteria from the temporary set. Repeat until there are five picks, or two or three for a small change, or no positive gain. The selection never changes the persistent coverage numerator.
4. For a remaining gap the catalog cannot express, retrieve nearby generic questions or use the observed graph gap directly. The model may adapt or combine them into a single project-local question with a criterion ID, rubric and source. New criteria require a user turn or concrete unfilled graph relation, a uniqueness check and the current generation budget. Project-specific wording, answers and evidence stay with the project. Any shared-catalog addition is a separately reviewed generic template.
5. Send only the chosen rubrics, rules, relevant facts, source spans and latest changes to the resolver. Each resolved criterion can count immediately. A partial or conflicting sibling remains in this batch. If the batch is superseded, any still-relevant open criterion can reenter selection. Store the open batch and cursor so a resumed chat recovers its place (`discovery_batches`; each criterion is a decision node, and the applicable set of a scope revision lives in `scope_criteria`, from which readiness is counted; see [database design](database-design.md#discovery-records)).

For example, one question covers delivery channel and recipient, another only channel, and a third covers cutoff. Picking the first consumes channel and recipient in **this batch’s selection set**. The cutoff question still adds one. If the user answers “email,” only the channel earns credit. Ask who receives the message. A later answer can also supply the deadline before anyone asks about it.

For 200 candidates and five picks there are at most 1,000 candidate scores. With ID sets the scoring work is O(k × n × c) when each candidate lists at most c criteria and set membership is constant time on average. Reading documents and model inference have separate costs. Benchmark greedy selection against simple topic order and a model ranking a bounded shortlist. Count repeated questions, important gaps missed, user turns, wrongly credited decisions and tokens per accepted decision. Include different project shapes and a blind, prespecified scoring rubric.

## One field per decision, one source per claim

Store criterion ID, scope, current value and basis, risk, evidence with turn and span IDs, applicable rule, premise IDs and status. Retain the revisions actually read by each call. The model proposes answers. The kernel checks the schema, current evidence, exact quoted spans and rule eligibility. A separate semantic check handles derived answers and costly explicit claims. Invalid replies leave the affected criterion pending and preserve validated siblings. A recommendation belongs in a separate field. [Prompt contracts and examples](opening-prompts.md)

Corrections walk reverse premise edges to dependent facts, question eligibility, architecture nodes, tasks and tests. A proposal for an unaffected field can still commit if its read set is current. Invalidate a derived claim when support disappears. Preserve independent user evidence and reevaluate the fact if another valid support path survives. Reject cyclic proofs. Relinking an item about the cutoff never authorizes a change to the delivery channel.

## Readiness with a changing scope

The denominator counts distinct **decisions**, independent of the number of questions and how often they are asked. Each assigned decision belongs to a scope and may inherit transitive prerequisites from project or shared contracts. Freeze this set per evaluation. Publish the scope revision, numerator, denominator, unresolved critical count and reason for any membership change. An empty or unknown scope reads “awaiting scope definition.”

| Display or check | Rule |
|---|---|
| Overall detail | Count all resolved applicable decisions divided by all applicable decisions, including deferred ones. Explicit values, validated permissible derivations and selected values within bounded delegation count once. |
| Ready for this planning scope | Start with the scoped set including its transitive project prerequisites. Only a user-authorized task or milestone deferral with an identified consumer and a verified independent interface can move a noncritical item outside this planning denominator. Removing a feature from this release separately removes its criteria. Every remaining criterion counts. Use exact counts to trigger readiness, since a rounded percentage can reach 100 early. |
| Critical open | Count unresolved architecture-shaping, hard-to-reverse or acceptance-critical decisions required for this milestone. An unanswered critical field blocks readiness even if all visible local feature fields are settled. |
| Deferred until a task | Show the decision, owner, consuming task or milestone and reason other work can proceed. The kernel reopens it through the arbiter as the consumer becomes eligible. That consumer waits until a verified value arrives. A deferred item with no safe boundary stays in planning scope. |
| Completeness pass | Check active domains, necessary shared dependencies, failure and boundary cases, non-functional constraints and observable acceptance examples. A missing answer in a required contract or example becomes a named graph gap. A documented reason can establish that a domain is inapplicable. |
| Transfer to planning and coding | On full scoped readiness and zero critical open items, construct the architecture. A newly discovered gap reopens the relevant criterion. When the resulting snapshot validates, publish affected architecture, plan, task and test records together. The first build waits for **Start build** on the [plan preview](planning-and-crew.md#plan-preview); later revisions under the developer's threshold dispatch automatically. Dispatch orders tasks grounded purely in `explicit` facts ahead of tasks that consume `derived` or `delegated` choices. The diff and its evidence are visible while work begins. |

Eight settled criteria out of twenty is 40%. Adding delivery might change it to eight out of twenty-four (33%). Say which four decisions were added. If all eighteen current planning decisions are resolved and the user explicitly defers two adapter choices with independent interfaces, the kernel state is 18/18 for planning and 18/20 overall. The UI says it in words: “Needed before building 18 of 18 ✓ · Everything we know 18 of 20 · 2 can wait until their tasks”, and explains every change to a total (“+4 since your last message: you added email delivery”). See [readiness display](interactive-architecture.md#readiness-display). A feature with five local answers and an open project-role prerequisite shows five out of six for planning.

Bound internal rounds, newly generated criteria per round and model cost. If successive rounds recycle the same gap or expand the scope without evidence, stop automatic generation and show the highest-impact question with its source. Changing the wording of a question cannot raise completeness. A genuinely new user requirement opens another snapshot. If the user has supplied everything, the internal rounds can complete without adding a user turn.

## Messages during a build

- **Read-only question.** Answer “Have you pushed?” from a timestamped remote observation or push receipt. A local commit alone leaves push status unknown.
- **New feature.** Open a scoped interview. Reuse current project facts, allow zero follow-ups where the evidence suffices, and keep any extra questions specific to the addition.
- **Existing feature change.** For “the kitchen wants print,” enumerate meanings such as add print and replace email, then inspect the tasks and contracts affected under each. The kernel hard-holds tasks affected under every plausible meaning at the next gated action, soft-holds possible-only impacts at a safe boundary, and leaves unrelated work running. The owner asks which behavior the user intended.
- **Execution control.** Route pause, resume, reprioritization and verified manual-step completion to kernel handlers. Explicit stop uses the direct control path. Mixed turns preserve their clause order and bindings. [Routing and holds](routing-design.md)

Revisions follow the changed decisions to affected architecture sections, plans, task briefs, UI contracts and tests. Use per-node read-set checks and publish a complete revision before reissuing changed work.
