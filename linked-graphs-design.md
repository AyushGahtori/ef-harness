# Independent work, routing and architecture changes

The architecture graph answers “Which behavior are we building, and what relies on it?” The runtime graph answers “Who owns that behavior and which attempt is working on it now?” A typed bridge connects them. A user can move a cutoff rule in the architecture and reach the planner responsible for the change without searching every worker’s chat.

## Independent work and shared contracts

For twelve independent tasks and four interchangeable workers, consecutively numbered groups of three are a reasonable initial assignment when their sizes match. The scheduler can offer the next ready task to a worker who finishes sooner. Group only work with compatible contracts and available isolated resources. A real prerequisite or shared migration belongs in a separate stage. Each worker receives a self-contained brief, selected skills and an attempt-specific workspace. The original task author owns the integration role. The observed 30% review and 70% wiring effort helps size that role.

The totals worker and print-page worker both use a versioned example row with dish ID, label and quantity. An independent verifier derives checks from the expected behavior, e.g. two separate soup orders display one row with quantity two. Each worker can implement its side against the pinned contract. The kernel runs the protected checks. The author wires the real functions into the production entry point and the kernel runs the feature journey against that combined result. Test fixtures carry contract versions. A stale fixture is replaced before the result can count. The [parallel integration design](parallel-feature-integration.md) describes task ownership and the verification sequence.

## Two graphs and their views

The proposed desktop coordinator uses TypeScript and SQLite. SQLite holds versioned project meaning and live runtime records in distinct namespaces. The JSON snapshot is the portable machine-readable interchange. A human can open Markdown and filtered Mermaid exports for the same revision. Each export declares its source revision and hash in its header or manifest. Runtime heartbeats never generate a new architecture revision. Git is authoritative for product code. Planners and workers fetch the currently authorized plan or brief through the coordinator.

| Graph | Example node properties | Typed relationships |
|---|---|---|
| Architecture | Feature aliases. Rule ID, value, unit or time zone, applicable workflow, evidence and version. Document section anchor. Contract version, example and acceptance check. | Feature contains rule. Section documents rule. Task implements rule or consumes contract. Test verifies rule. |
| Runtime | Agent number, owner role and session reference. Assignment ID, task, attempt, workspace, contract versions, activity, state and checkpoint. | Planner delegates to worker. Planner authored brief. Worker holds assignment. Parent task contains child tasks. |
| Bridges | Source and target each include project, namespace and stable ID. Roles describe responsibility. An assignment identifies one run. | Architecture rule is owned by runtime planner role. Architecture task is executed as runtime assignment. |

Code allocates stable IDs. A split or merge creates new IDs, retains the old node as retired and records supersession edges. The kernel rejects dangling references. Allocate each new agent a never-reused project-local number, e.g. A0014, inside a transaction. A worker can change session while its role and audit history remain discoverable. A replacement gets its own number. Roles, assignments and integration branches have leases with holder, expiry and increasing epoch. A replacement receives a higher epoch. Every state-changing action and publish operation validates its epoch at the transaction boundary. A stale worker may leave a diff in its old worktree. Only the current attempt can publish. On restart, match live processes to their recorded identity and fence, reattach recoverable attempts and reclaim or terminate superseded ones.

## Routing and propagation

1. In the active project, resolve explicit IDs, reply targets and selected nodes first. For “make that list printable too,” search aliases and titles with the referenced turns and active feature. Give the cheap read-only model matching reasons and a bounded candidate list (start evaluation at five). Widen once by typed neighbors or ask which list.
2. Resolve a selected requirement through its typed ownership edge. Status requests read receipts directly. Validate target and lease again upon delivery. A move to another owner while routing preserves the message in the durable role inbox.
3. For a material feature change, walk reverse usage edges using a queue and visited set. `implements`, `consumes-contract` and `verifies` propagate possible invalidation. `documents` identifies an export to refresh. Similar languages, topics and technology tags supply candidate hints only. Cross-check owned paths, actual import/call edges and integration seams. A bounded traversal that leaves unknown dependencies emits a pending impact check for the owner.
4. Compute an affected set for each plausible interpretation. Tasks affected by all readings receive a hard hold at their next tool boundary. Tasks affected by some readings finish only their current bounded step and quarantine its result. Other assignments continue. An unresolved subject alone does not justify pausing all matching features. Track reasons so clearing one hold cannot erase an explicit user pause.

Index by `(project, namespace, id)` and by `(project, source_namespace, source_id, edge_type)` with the target-side equivalent. An exact ID lookup reads the matching range. Traversal cost grows with the affected subgraph and each adjacency lookup. Evaluate shortlist recall, wrong owner, unsolicited mutation, unnecessary user questions, wrongly paused tasks, latency and tokens on labeled cases. Include ambiguity, owner replacement and a reply to an earlier topic. [Routing example and diagram](agent-graph-routing.md)

## A cutoff edit and a crash

A change to R17 from 11:00 to 10:45 reaches its feature description, backend validation, UI instructions and boundary test. The owner bridge reaches the kitchen planner. An order submitted at 10:50 must now receive the agreed response. Equality at 10:45 and the applicable time zone require their own known decisions. Graph construction can reopen one of those criteria before publishing.

The planner submits a scoped delta. The kernel compares observed node and adjacency versions, applies the canonical changes, writes versioned task briefs and appends outbox events in one short transaction. The global revision labels snapshots. Disjoint edits may commit while the cutoff owner is thinking. A conflicting edit to the same rule must be resolved on meaning. Consumers get idempotent delivery per event and consumer. A failed Markdown, JSON or Mermaid export is regenerated for the already committed revision. The [revision and recovery design](linked-architecture-revisions.md) covers hand edits, recovery and rollback of merged behavior.
