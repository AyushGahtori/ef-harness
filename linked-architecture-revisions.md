# Publishing a requirement change and recovering after interruption

One change to the kitchen cutoff from 11:00 to 10:45 affects its backend rule, the order page, the feature plan and the boundary test. Its typed ownership link reaches the kitchen planner. The planner checks the time zone, the policy exactly at 10:45 and what a 10:50 submission should do. A gap discovered while connecting the graph reopens the criterion and goes to the shared question queue.

## One authoritative revision

The proposed kernel keeps versioned architecture nodes, typed edges, decisions and brief contents in SQLite. Runtime leases and assignments have separate records. JSON snapshots, human Markdown and Mermaid are projections of a specific committed revision. Git tracks product code. The worker fetches its active self-contained brief and pinned contracts, acceptance references and skills from the coordinator by task ID and lease. A historical Markdown copy in its worktree cannot authorize work.

1. Persist a submitted steer under its message ID. Coalesce queued steers per feature when the planner next takes work. Record the exact origin of each change and any explicit correction. Capture versions for every node read or written, including contract and evidence nodes. Version relevant edge collections and negative lookups as well. For example, check the consumers-of-R17 collection so a newly added UI consumer cannot slip past an old impact traversal. A create also checks its expected absence or unique key.
2. Traverse incoming typed usage edges with a visited set. `implements`, `consumes-contract` and `verifies` can invalidate work. `documents` refreshes an export. Fold in verified imports or shared paths as dependency candidates. If effects remain unclear at the traversal bound, flag them for the owner and gate affected acceptance until resolved. Include a removal or revert task for already merged behavior.
3. Stage the proposed writes under a change ID. In a short SQLite write transaction, the kernel validates the planner lease epoch, scoped read/write versions, relevant adjacency versions, referenced IDs and acceptance coverage. Apply canonical node and edge changes, preserve immutable history, write the new briefs, allocate a display revision, record the consumed steer and insert distinct outbox events atomically. A repeat of the same change ID returns the previous outcome. Disjoint changes may both publish. A stale impact set gets recomputed. Competing values for R17 are compared semantically. A clear later correction supersedes its cited predecessor, while two unclear requests go back to their owner. Repeated contention gets fair, ordered access to the affected keys for a brief commit.
4. The snapshot exporter reads exactly the committed revision. Write immutable files by revision, verify checksums and references, and publish their manifest only after the files are complete. Show export status and the last ready revision while generation is pending. Escape user labels, limit or paginate feature views, and parse Mermaid before marking that view ready. A failed view can be regenerated from the committed data. A hand-edited export is retained and imported as a proposed steer through its IDs and base version; detection, section markers, three-way conflicts and deletes are specified in [knowledge database](knowledge-database.md#1-direct-edits-to-the-generated-markdown).
5. Each event has a stable ID and intended consumers. Deliver at least once, with a durable receipt keyed by `(event_id, consumer_id)` in the same transaction as that consumer’s state update. A contract-change event and a dependency-ready event in one revision both reach the task. For external actions use the action ledger and reconcile unknown outcomes before retry. Before granting a tool action or accepting a result, check the current lease, brief and applicable contract versions. An unrelated revision can advance while a valid worker finishes.

## Crash, resumption and undo

A crash before commit leaves the prior scope and the pending steer. A crash after commit leaves the new graph, briefs and outbox together. On restart, recover queued steers, missing exports and undelivered events, reconcile process and action receipts, and fence expired attempts. Never resume a worker from a chat transcript alone. Its checkpoint records the task, attempt, contract vector, session reference, WIP Git ref and pending side effects. Resume an additive clarification with the existing session if available. A contradictory contract starts a fresh session with the new brief and the old WIP diff clearly identified and rechecked.

Undo is a forward revision linked to the change being reversed. Restore its decisions, re-run the current impact analysis and issue code-removal or revert tasks where work was merged. External actions such as an email already sent retain their original receipt. Before proposing an undo, inventory what the change added (migrations, packages, shared types, routes) and who else uses each piece; shared pieces and data are kept unless the developer explicitly removes them. [Undoing a merged feature](stops-undo-and-reentry.md#undoing-a-feature-after-it-merged)

Exercise a disjoint login edit, a simultaneous new consumer of R17, incompatible cutoff edits, and a restart immediately before commit, after commit and after a consumer acts but before delivery acknowledgment. Verify one authoritative cutoff, both distinct events, regeneration of a failed diagram, consistent briefs, preservation of unrelated work and zero duplicate external actions.
