# Stops, undo and coming back later

Three human moments the crash-recovery design doesn't cover by itself: the money or plan allowance runs out mid-build, the developer wants a merged feature gone, and the developer returns after days away. The rule behind all three: **work is never lost, and the harness always picks up exactly where it stopped.** Research: [coexistence, undo and re-entry](research/coexistence-undo-and-reentry.md).

## Decisions in plain words

1. **Work is saved continuously, not only at the end.** Every worker checkpoints at every turn boundary: a WIP commit on a harness ref, the session reference and a short handoff note, recorded in `attempt_checkpoints` together with the contract versions in use and any pending external effects ([schema](schema/state.sql)). A limit, crash or closed laptop loses at most the turn in progress.
2. **Hitting a limit pauses; it never fails.** Tasks move to *Parked* with their checkpoint. The developer chooses how to continue: add budget, switch models, wait for a plan reset, or finish by hand.
3. **Unfinished work stays private.** Half-done features stay on harness branches and are never landed. They can be exported as normal Git branches at any time.
4. **Undo is planned, not blind.** Undoing a feature first lists what it added and who else uses each piece. Shared pieces stay; data stays unless the developer explicitly approves removing it.
5. **Coming back starts with a summary, not with running.** The harness reconciles everything that changed while it was closed, shows it, and waits for **Resume**.

## When the budget or allowance runs out

### Stages

| Level | What happens | Developer sees |
|---|---|---|
| 50% / 80% | Alerts only | Meter turns amber; one digest item |
| 90% (*wind-down*) | No new attempts start; running attempts finish their current step. A small reserve is kept for checkpointing and verification of finished candidates | “Budget nearly used · finishing current steps” |
| 100% (*stopped*) | Every attempt checkpoints and parks | Stop card (below); office lights go to evening mode |
| Plan window closed | Same as stopped, but with a known or estimated reset time | “Waiting for allowance · resumes ~14:05” and optional auto-resume |

### What is saved for each unfinished task

| Item | Where |
|---|---|
| WIP code | Commit on `refs/harness/checkpoints/<task>/<n>` |
| The attempt branch | `harness/t/<task>/<attempt>`, a normal Git branch |
| Session reference | Codex thread ID, Claude session ID, Cursor agent ID, or our own loop's transcript |
| Handoff note | Generated by code from events: brief version, steps done and remaining (from the agent's plan), files changed, last check results, last failing check |
| Ledger state | Exact spend and reservations, settled |

### The stop card

```
Budget reached: $10.00 of $10.00 · 9 of 12 tasks done · F12 print is 3 tasks short
Your work is saved. Nothing has been lost.

[Add budget]            +$2 is enough for the remaining 3 tasks (estimate $1.40–2.10)
[Use cheaper models]    Remaining 3 tasks on Junior/Mid: estimate $0.70–1.10
[Switch connection]     Continue on your ChatGPT plan (≈2% of weekly share)
[Wait for reset]        Copilot allowance resets Dec 1
[Finish by hand]        Export 3 branches with notes
[Keep parked]
```

Each option shows its estimate first. **Use cheaper models** opens the plan preview for the remaining tasks only. Choosing any option resumes from the checkpoints: sessions resume where the runtime supports it; otherwise a fresh session gets the brief plus the labeled WIP diff.

### Finish by hand (export)

**Export** creates readable branches from the checkpoints, e.g. `wip/T10-print-dialog`, `wip/T11-print-styles`, and the feature branch `wip/F12-print` with all accepted tasks. Each gets its handoff note, shown in the app and optionally written as a `HANDOFF-T10.md` file outside the commit or as the commit message. The developer can then work normally; when done, the [I fixed it myself](editor-coexistence.md#i-fixed-it-myself) flow verifies and accepts each task.

A partially finished feature is never landed into the developer's branch. If it was designed behind a feature flag, landing with the flag off is offered as an explicit option.

## Undoing a feature after it merged

“Undo the print feature” is routed as a current-feature change. The planner runs an **undo inventory** before proposing anything.

### 1 · Inventory what the feature added

From the graph, Git history and code search: commits, files, routes, exported types and functions, database migrations (tables, columns, indexes), packages, environment variables, config entries, background jobs, and external effects (emails sent, webhooks registered).

### 2 · Find who else uses each piece

Graph edges, the import graph, package usage, database column usage in code, and later migrations that build on this feature's migrations.

### 3 · Classify and propose

```
Undo F12 Kitchen print
  Remove   14 files · route /kitchen/print · Print button · 2 tests
  Keep     PrintRow type · used by F15 Reports → ownership moves to shared package
  Keep     package html-to-image · also used by F15
  Data     column orders.printed_at · 312 rows have values
           ○ Keep the column (recommended) ○ Stop writing, drop later ○ Export then drop now
  Can't undo  41 print jobs already sent (recorded receipts)
  Then     Full regression for F13, F14, F15
[Apply undo]  [Cancel]
```

| Category | Default |
|---|---|
| Used only by this feature | Remove |
| Shared with another feature | Keep; move ownership to the consumer or shared foundation |
| Holds data | Keep. Removal requires explicit choice; dropping uses expand-then-contract (stop writing now, drop in a later release) and an export first |
| Package | Remove only if nothing else imports it; the integrator updates the lockfile |
| External effect | Can't be undone; shown with its receipts; compensating actions (e.g. unregister a webhook) become tasks if possible |

### 4 · Execute

- **Fast path:** if the feature landed as one merge and no later commit touched its files, revert that merge commit and run the regression.
- **Planned path:** otherwise, removal tasks per area, with the same verification as any task, followed by the regression.
- Undoing an undo is another forward revision.

## Coming back later

### Reconciliation on open (before anything runs)

| Check | Looks for |
|---|---|
| Coordinator state | Last committed revision, pending outbox, leases (expired workers fenced) |
| Worktrees | Missing or modified harness worktrees; recreate from checkpoints |
| Developer's repo | New commits on the base branch, dirty files, branch switches, edits inside harness worktrees |
| Dependencies | Lockfile changes; installed tool versions |
| Connections | Expired tokens or keys, plan windows reset, price or model catalog changes |
| Agent CLIs | Version changes → rerun the adapter conformance suite |
| Questions | Each open question is rechecked: still relevant after the new commits and answers? |

### Welcome-back screen

```
Welcome back to kitchen-app · last active Friday 18:40 (2 days ago)

Finished while you were away     F13 ordering landed on harness/integration · 6 tasks
Parked                           3 tasks at checkpoints (F12 print, ~70% done) · reason: budget
Waiting on you                   2 questions · 1 changed since Friday (recap below)
Your changes                     3 commits on main touching 5 files · 1 overlaps T10 → will refresh T10
Connections                      ChatGPT weekly share reset ✓ · Cursor key expires in 4 days
Budget                           $0.00 left of $10 · top up to continue F12

[Resume]   [Review changes first]   [Open the board]
```

- **Nothing runs until Resume.**
- Each waiting question gets a **recap**: “You were deciding whether managers can edit orders after cutoff, because T10 needs it. Since Friday you committed a change to `orders/edit.ts`, which now lets managers edit until 11:15. Is that the answer?”
- A question that the developer's own commits answered is offered as **Looks answered by your commit 3f2a · Confirm**.
- Questions older than a week are re-validated before showing; obsolete ones are retired with a note.

## Edge cases

| Situation | Behavior |
|---|---|
| Laptop sleeps mid-turn | On wake, the in-flight call is treated as an unknown outcome; the attempt resumes from its last checkpoint; ambiguous paid calls are reconciled before retry. |
| Budget raised while tasks are parked | Parked tasks resume in priority order; nothing restarts from scratch. |
| Developer deletes checkpoint refs | Those tasks restart from their brief; finished work on integration is unaffected. |
| Export, then the developer abandons the feature | The wip branches remain theirs; the harness marks the feature *abandoned* and removes its tasks from the plan. |
| Undo requested while another feature is mid-build and uses the piece | That piece is classified as shared; the running feature keeps it. |
| Model used for a parked task was retired | Roster fallback chooses the next model for that level; the welcome screen mentions it. |
